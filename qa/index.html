GLF-001

Pipeline Android bloqueado por configuración Firebase

Severidad Alta Estado Resuelto

Resumen: El pipeline de GitHub Actions no lograba generar correctamente el build Android debido a una configuración requerida por Firebase que no estaba disponible durante la ejecución.

Qué ocurrió: El workflow fallaba durante processReleaseGoogleServices porque el entorno de CI no encontraba google-services.json, necesario para completar el build de la aplicación.

Resolución y validación: Se ajustó la configuración del pipeline para disponer del archivo requerido durante el proceso de build sin incorporarlo directamente al repositorio. Después del cambio realicé un re-test del pipeline, verificando que la ejecución finalizara correctamente y que se generaran los artifacts correspondientes para Android y web.

Prácticas aplicadas: Debugging de CI/CD · Testing de build · GitHub Actions · Gestión de configuración · Re-test · Verificación de artifacts · Validación post-fix

Evidencias

GLF-002

Error crítico durante el inicio de Flutter Web

Severidad Alta Estado Resuelto

Resumen: La versión web de la aplicación presentaba un error de runtime durante el inicio e impedía acceder normalmente al sistema.

Qué ocurrió: Al cargar la aplicación aparecía un error asociado al uso de un valor nulo durante el arranque. El problema impedía que la interfaz llegara correctamente a la pantalla de acceso.

Resolución y validación: Se investigó el flujo de inicialización de la aplicación y se realizaron ajustes para evitar el fallo durante el arranque. Luego ejecuté un re-test del inicio de Flutter Web, comprobando que la aplicación cargara nuevamente y llegara correctamente a la pantalla de login.

Prácticas aplicadas: Debugging de runtime · Flutter Web · Análisis de errores · Testing funcional · Re-test · Validación post-fix

Evidencias

GLF-003

Validación de despliegue web en Firebase Hosting

Tipo Validación de deploy Estado Validado

Resumen: Después de estabilizar el proceso de build, se validó que la versión web quedara correctamente publicada y accesible desde Firebase Hosting.

Qué se validó: Era necesario comprobar no solo que el workflow terminara correctamente, sino también que el build generado se publicara y que la aplicación pudiera abrirse desde el entorno desplegado.

Pruebas realizadas: Se verificó la ejecución exitosa de GitHub Actions, la generación de artifacts, la publicación en Firebase Hosting y el acceso efectivo a la aplicación desde navegador.

Prácticas aplicadas: Validación de deploy · CI/CD · GitHub Actions · Firebase Hosting · Verificación de artifacts · Validación post-deploy

Evidencias

CI/CD y configuración sensible Trabajar con el fallo del build me permitió entender mejor cómo manejar configuraciones necesarias para Firebase dentro de un pipeline sin depender de archivos sensibles expuestos directamente en el repositorio.
Un build exitoso no garantiza que la aplicación funcione Después de resolver el pipeline, encontré un error que aparecía recién durante la ejecución de Flutter Web. Eso me ayudó a diferenciar problemas de compilación de problemas de runtime y a entender que la validación debe continuar después del build.
Debugging de runtime Investigar el error de inicio me permitió trabajar con fallos que solo aparecen al ejecutar la aplicación y comprobar la importancia de validar nuevamente el comportamiento después de cada corrección.
Validación post-deploy El despliegue en Firebase me mostró que un workflow exitoso tampoco alcanza por sí solo: es necesario comprobar que la versión publicada sea realmente accesible en el entorno final.
Trabajo sobre una aplicación existente Este proyecto me permitió practicar cómo comprender una base de código que no desarrollé desde cero, intervenir de forma puntual y validar cada cambio antes de continuar.

QA-PROCTO-001

Aislamiento de exámenes entre docentes

Severidad Alta Estado Resuelto

Resumen: Se detectó que el acceso a los exámenes necesitaba aislar correctamente la información correspondiente a cada docente.

Qué ocurrió: El listado de exámenes no garantizaba en todos los casos que cada usuario visualizara únicamente los recursos asociados a su cuenta. En una plataforma multiusuario, esto podía afectar la privacidad y separación de información entre docentes.

Resolución y validación: Se reforzó la autenticación y el filtrado de exámenes por propietario y membresías. Después del ajuste, se realizó una prueba de regresión sobre los flujos de acceso y listado de exámenes, verificando que cada docente pudiera visualizar únicamente los recursos correspondientes a su usuario y que el comportamiento previo esperado continuara funcionando correctamente.

Prácticas aplicadas: Testing funcional · Pruebas de regresión · Control de acceso · Validación de permisos · API/backend debugging

Evidencias

QA-PROCTO-002

Compatibilidad con PostgreSQL en rutas de examen

Severidad Alta Estado Resuelto

Resumen: Durante la migración a PostgreSQL se detectaron incompatibilidades en consultas utilizadas por distintas funcionalidades del examen.

Qué ocurrió: Algunas rutas utilizaban consultas SQL raw con placeholders o referencias a columnas que no eran compatibles con PostgreSQL. Esto provocaba errores en funcionalidades relacionadas con preguntas, chat, paper y revisión.

Resolución y validación: Se ajustaron las consultas afectadas y se incorporaron controles para facilitar la detección de errores. Luego se realizaron pruebas de integración entre API y base de datos, seguidas de una regresión sobre los flujos afectados, para confirmar que las funcionalidades continuaran respondiendo correctamente después de la migración.

Prácticas aplicadas: Testing de integración · Pruebas de regresión · SQL debugging · API testing · PostgreSQL · Validación post-fix

Evidencias

QA-PROCTO-003

Error 404 al acceder a la revisión del examen

Severidad Alta Estado Resuelto

Resumen: Después de finalizar y corregir un examen, el alumno no podía acceder correctamente a la revisión desde la opción “Ver revisión”.

Qué ocurrió: Al intentar ingresar, la interfaz no cargaba el examen corregido. Mediante DevTools y la pestaña Network se identificó que la solicitud al recurso de revisión devolvía un error HTTP 404.

Resolución y validación: Se analizó la integración entre frontend y backend hasta localizar el origen del error y se corrigió el acceso al recurso correspondiente. Después del fix se realizó un re-test del defecto y una prueba de regresión del flujo completo de revisión: acceso desde “Ver revisión”, recuperación de datos, visualización de respuestas y feedback, y generación de la versión imprimible/PDF.

Prácticas aplicadas: Testing funcional · Re-test · Pruebas de regresión · DevTools / Network · HTTP · Debugging frontend/backend

Evidencias

QA-PROCTO-004

Flujo de corrección manual y feedback docente

Tipo Validación funcional Estado Validado

Resumen: Se validó el recorrido completo de corrección manual de un examen y la posterior visualización de resultados por parte del alumno.

Qué se validó: El flujo debía mantener consistencia entre las respuestas del alumno, la calificación asignada, el feedback docente y la información presentada posteriormente en la revisión.

Pruebas realizadas: Se ejecutó una prueba funcional end-to-end desde la bandeja de corrección docente hasta la revisión final del examen. Se verificaron estados, calificaciones, comentarios generales y la generación de la versión imprimible/PDF.

Prácticas aplicadas: Testing funcional · Validación end-to-end · Reglas de negocio · Consistencia de datos · Validación de salida PDF

Evidencias

QA-PROCTO-005

Validación del sistema antifraude

Tipo Validación funcional Estado Validado

Resumen: Se comprobó el comportamiento de una de las reglas antifraude implementadas durante la realización del examen.

Qué se validó: Ante una acción contemplada como no permitida, el sistema debía detectar el evento, mostrar una advertencia al alumno y aplicar correctamente la penalización correspondiente.

Pruebas realizadas: Se ejecutó una prueba funcional sobre el flujo antifraude, provocando intencionalmente la condición a validar. Se comprobó la aparición de la advertencia, el descuento de una vida y la posibilidad de regresar al examen respetando las reglas establecidas.

Prácticas aplicadas: Testing funcional · Casos negativos · Reglas de negocio · Validación de estados · Antifraude · UX de errores y advertencias

Evidencias

Control de acceso y regresión Entendí que validar permisos no implica solo comprobar que el fix funcione, sino también revisar que no afecte otros flujos ni permita accesos indebidos.
Integración API–base de datos Trabajar con la migración a PostgreSQL me permitió ver cómo un cambio en persistencia puede impactar distintas funcionalidades y por qué es importante combinar debugging con pruebas de integración.
Diagnóstico con DevTools El error 404 en la revisión de exámenes me ayudó a usar Network y las respuestas HTTP para identificar con más precisión dónde se originaba una falla.
Validación end-to-end El flujo de corrección docente me mostró la importancia de probar procesos completos y verificar que estados, calificaciones, feedback y resultados mantengan coherencia entre sí.
Casos negativos y reglas de negocio Las pruebas del sistema antifraude me permitieron trabajar con escenarios provocados intencionalmente para comprobar que advertencias, penalizaciones y cambios de estado funcionaran como se esperaba.
