GLF-001

Pipeline Android bloqueado por configuración Firebase

Severidad Alta Estado Resuelto

Descripción breve: El workflow de GitHub Actions fallaba durante la generación del APK Android porque el build no encontraba el archivo google-services.json, necesario para compilar la app con Firebase.

Resolución breve: Se ajustó el pipeline para reconstruir el archivo desde un secret de GitHub Actions antes de ejecutar el build, permitiendo generar correctamente el APK y el build web como artifacts.

Evidencias

GLF-002

Crash crítico durante el inicio de Flutter Web

Severidad Alta Estado Resuelto

Descripción breve: La versión web mostraba un error fatal al iniciar, con mensajes relacionados a valores nulos durante el arranque de la aplicación.

Resolución breve: Se revisó el flujo de inicialización de Firebase y el arranque web, incorporando diagnóstico por etapas y ajustes defensivos para estabilizar la carga inicial.

Evidencias

GLF-003

Validación de despliegue Web en Firebase Hosting

Severidad Media Estado Resuelto

Resolución breve: Se verificó el workflow exitoso, la generación de artifacts y el estado de Firebase Hosting, confirmando que la aplicación quedara publicada y operativa.

QA-PROCTO-001

Seguridad y aislamiento de owner entre docentes

Severidad Alta Estado Resuelto

Resumen: Se corrigió un problema de aislamiento entre docentes en el listado y creación de exámenes. El flujo pasó a requerir autenticación y a filtrar los exámenes por owner y membresías.

Qué ocurrió: El listado de exámenes no garantizaba correctamente que cada docente visualizara solo los exámenes asociados a su usuario. En una plataforma multiusuario, esto podía afectar la separación de datos entre propietarios.

Cómo se resolvió / validó: Se incorporó autenticación obligatoria en endpoints sensibles, filtrado por ownerId y membresías, creación de ExamMember con rol OWNER y un endpoint de recuperación para exámenes legacy. La validación se documenta mediante commit histórico, diff del fix y código actual.

Competencias demostradas: Seguridad backend · Control de acceso · Multi-tenant isolation · Debugging de API · Modelado de ownership · Remediación de datos legacy

Evidencias

QA-PROCTO-002

Migración y reparación de PostgreSQL

Severidad Alta Estado Resuelto

Resumen: Se corrigieron consultas raw incompatibles con PostgreSQL y se agregó reparación defensiva para tablas lite con columnas inconsistentes.

Qué ocurrió: Durante la migración a PostgreSQL, distintas rutas del examen dependían de consultas SQL raw con placeholders y nombres de columnas no compatibles con el motor actual. Esto afectaba funcionalidades como chat, paper, preguntas y revisión.

Cómo se resolvió / validó: Se ajustaron placeholders a sintaxis PostgreSQL, se normalizaron nombres de columnas camelCase con comillas, se agregaron rutinas de reparación de esquema lite y logging específico para errores SQL. La validación se documenta mediante commit histórico, diff del fix y código actual.

Competencias demostradas: PostgreSQL · Debugging de SQL raw · Migración de base de datos · Reparación defensiva de esquema · Observabilidad técnica · Integración API/base de datos

QA-PROCTO-005

Validación del sistema antifraude

Severidad Alta Estado Resuelto

Resumen: Validación del comportamiento antifraude frente a una acción no permitida durante el examen.

Qué ocurrió: El sistema detecta una acción no permitida durante el examen y muestra una advertencia al alumno indicando que se descontó una vida.

Cómo se resolvió / validó: Se verificó visualmente la advertencia mostrada al alumno y la respuesta esperada del flujo de examen.

Competencias demostradas: Validación funcional, monitoreo de reglas antifraude y revisión de comportamiento crítico para examen online.
