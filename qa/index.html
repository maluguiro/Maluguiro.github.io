GLF-001

Pipeline Android bloqueado por configuración Firebase

Tipo Validación funcional Estado Validado

Descripción breve: El workflow de GitHub Actions fallaba durante la generación del APK Android porque el build no encontraba el archivo google-services.json, necesario para compilar la app con Firebase.

Resolución breve: Se ajustó el pipeline para reconstruir el archivo desde un secret de GitHub Actions antes de ejecutar el build, permitiendo generar correctamente el APK y el build web como artifacts.

Evidencias

GLF-002

Crash crítico durante el inicio de Flutter Web

Severidad Alta Estado Resuelto

Descripción breve: La versión web mostraba un error fatal al iniciar, con mensajes relacionados a valores nulos durante el arranque de la aplicación.

Resolución breve: Se revisó el flujo de inicialización de Firebase y el arranque web, incorporando diagnóstico por etapas y ajustes defensivos para estabilizar la carga inicial.

Evidencias

GLF-003

Validación de despliegue Web en Firebase Hosting

Severidad Media Estado Resuelto

Descripción breve: Después de estabilizar el build, era necesario validar que la versión web quedara correctamente publicada y accesible desde Firebase Hosting.

Resolución breve: Se verificó el workflow exitoso, la generación de artifacts y el estado de Firebase Hosting, confirmando que la aplicación quedara publicada y operativa.

GLF-004

Hardening de Firebase Hosting y reglas de seguridad

Severidad Alta Estado Pendiente de documentación

QA-PROCTO-001

Aislamiento de exámenes entre docentes

Severidad Alta Estado Resuelto

Resumen: Se detectó que el acceso a los exámenes necesitaba aislar correctamente la información correspondiente a cada docente.

Qué ocurrió: El listado de exámenes no garantizaba en todos los casos que cada usuario visualizara únicamente los recursos asociados a su cuenta. En una plataforma multiusuario, esto podía afectar la privacidad y separación de información entre docentes.

Resolución y validación: Se reforzó la autenticación y el filtrado de exámenes por propietario y membresías. Después del ajuste, se realizó una prueba de regresión sobre los flujos de acceso y listado de exámenes, verificando que cada docente pudiera visualizar únicamente los recursos correspondientes a su usuario y que el comportamiento previo esperado continuara funcionando correctamente.

Prácticas aplicadas: Testing funcional · Pruebas de regresión · Control de acceso · Validación de permisos · API/backend debugging

Evidencias

QA-PROCTO-002

Compatibilidad con PostgreSQL en rutas de examen

Severidad Alta Estado Resuelto

Resumen: Durante la migración a PostgreSQL se detectaron incompatibilidades en consultas utilizadas por distintas funcionalidades del examen.

Qué ocurrió: Algunas rutas utilizaban consultas SQL raw con placeholders o referencias a columnas que no eran compatibles con PostgreSQL. Esto provocaba errores en funcionalidades relacionadas con preguntas, chat, paper y revisión.

Resolución y validación: Se ajustaron las consultas afectadas y se incorporaron controles para facilitar la detección de errores. Luego se realizaron pruebas de integración entre API y base de datos, seguidas de una regresión sobre los flujos afectados, para confirmar que las funcionalidades continuaran respondiendo correctamente después de la migración.

Prácticas aplicadas: Testing de integración · Pruebas de regresión · SQL debugging · API testing · PostgreSQL · Validación post-fix

Evidencias

QA-PROCTO-003

Error 404 al acceder a la revisión del examen

Severidad Alta Estado Resuelto

Resumen: Después de finalizar y corregir un examen, el alumno no podía acceder correctamente a la revisión desde la opción “Ver revisión”.

Qué ocurrió: Al intentar ingresar, la interfaz no cargaba el examen corregido. Mediante DevTools y la pestaña Network se identificó que la solicitud al recurso de revisión devolvía un error HTTP 404.

Resolución y validación: Se analizó la integración entre frontend y backend hasta localizar el origen del error y se corrigió el acceso al recurso correspondiente. Después del fix se realizó un re-test del defecto y una prueba de regresión del flujo completo de revisión: acceso desde “Ver revisión”, recuperación de datos, visualización de respuestas y feedback, y generación de la versión imprimible/PDF.

Prácticas aplicadas: Testing funcional · Re-test · Pruebas de regresión · DevTools / Network · HTTP · Debugging frontend/backend

Evidencias

QA-PROCTO-004

Flujo de corrección manual y feedback docente

Tipo Validación funcional Estado Validado

Resumen: Se validó el recorrido completo de corrección manual de un examen y la posterior visualización de resultados por parte del alumno.

Qué se validó: El flujo debía mantener consistencia entre las respuestas del alumno, la calificación asignada, el feedback docente y la información presentada posteriormente en la revisión.

Pruebas realizadas: Se ejecutó una prueba funcional end-to-end desde la bandeja de corrección docente hasta la revisión final del examen. Se verificaron estados, calificaciones, comentarios generales y la generación de la versión imprimible/PDF.

Prácticas aplicadas: Testing funcional · Validación end-to-end · Reglas de negocio · Consistencia de datos · Validación de salida PDF

Evidencias

QA-PROCTO-005

Validación del sistema antifraude

Tipo Validación funcional Estado Validado

Resumen: Se comprobó el comportamiento de una de las reglas antifraude implementadas durante la realización del examen.

Qué se validó: Ante una acción contemplada como no permitida, el sistema debía detectar el evento, mostrar una advertencia al alumno y aplicar correctamente la penalización correspondiente.

Pruebas realizadas: Se ejecutó una prueba funcional sobre el flujo antifraude, provocando intencionalmente la condición a validar. Se comprobó la aparición de la advertencia, el descuento de una vida y la posibilidad de regresar al examen respetando las reglas establecidas.

Prácticas aplicadas: Testing funcional · Casos negativos · Reglas de negocio · Validación de estados · Antifraude · UX de errores y advertencias
